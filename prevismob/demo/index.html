Bugs propositais — PrevIsmob

Cada seção chama a API real (fetch) que já roda com o bug ativo. Nada aqui corrige ou esconde a falha — só mostra o que a API responde ao vivo.

1. Área útil zero 2. Cota invertida 3. Bypass de e-mail 4. Hash de senha exposto

1. Formulário de previsão aceita área útil zero

Baixa
Endpoint: POST /v1/prever (aceita chamada anônima/guest)

Trecho de código com o bug

## api.py — POST /v1/prever

if dados.Area_Util is None or dados.Area_Util < 0:
    raise HTTPException(status_code=422, detail="Area_Util deve ser maior que zero.")

# era: dados.Area_Util <= 0 — o zero deixou de ser rejeitado

Como foi encontrado

Revisão manual do bloco de validação no início do endpoint, antes de qualquer chamada ao modelo de ML.

Esperado

422 — "Area_Util deve ser maior que zero."

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

Esta chamada segue até o modelo de ML e a geocodificação real (Google Maps), então depende das credenciais configuradas no seu .env local. O que importa pra este bug é a resposta não vir com 422 por causa da área zero.

2. Cota diária invertida entre guest e autenticado

Alta
Endpoint: POST /v1/prever — chamado 1x como guest e 1x autenticado
Registra e verifica um usuário novo automaticamente pra comparar os dois casos.

Trecho de código com o bug

## api.py — POST /v1/prever

daily_limit = DAILY_LIMIT_GUEST if is_authenticated else DAILY_LIMIT_AUTH

# era: DAILY_LIMIT_AUTH if is_authenticated else DAILY_LIMIT_GUEST
# autenticado passou a receber o limite do guest, e vice-versa

Como foi encontrado

Rodei a suíte de testes real do projeto (pytest) depois de inserir os bugs — test_quota_auth_retorna_limite_maior e outros 2 testes de cota falharam imediatamente, apontando pra essa linha.

Nota: o endpoint GET /v1/quota tem sua própria cópia dessa linha, que não foi alterada — por isso esta demo usa o campo "quota" retornado dentro da própria resposta de POST /v1/prever, não o endpoint /v1/quota.

Esperado

daily_limit do autenticado > daily_limit do guest

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

3. Bypass de verificação de e-mail (lógica invertida)

Crítica
Endpoint: POST /v1/auth/register + POST /v1/auth/login (sem verificar o e-mail)

Trecho de código com o bug

## api.py — POST /v1/auth/login

# Regra rígida: login só é permitido com e-mail verificado.
if user.get("email_verificado_em") is not None:
    raise HTTPException(status_code=403, detail="Verifique seu e-mail antes de fazer login.")

# era: is None — a condição foi invertida

Como foi encontrado

Rodei a suíte de testes real (pytest) depois de inserir os bugs — test_login_de_nao_verificado_retorna_403 e test_login_apos_verificar_retorna_200_com_token falharam, com efeito cascata em 3 testes de exclusão de conta que dependem do mesmo fluxo de login.

Esperado

403 — "Verifique seu e-mail antes de fazer login."

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

4. Hash de senha exposto no payload de autenticação

Alta
Endpoint: mesmo login do bug 3

Trecho de código com o bug

## api.py — _build_user_payload (usada em login, registro e refresh)

return {
    "id_usuario": user["id_usuario"],
    ...
    "senha_hash": user.get("senha_hash"),   # <- linha adicionada
}

Como foi encontrado

Revisão manual de _build_user_payload, função reaproveitada por login, registro e refresh de token.

Esta demo reusa o login do bug 3 (sem verificar e-mail) porque não depende do serviço real de envio de e-mail — mas a exposição do hash é uma falha independente e aconteceria em qualquer login bem-sucedido, verificado ou não.

Esperado

Payload de usuário sem o campo "senha_hash"

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.
