1. Validação de matrícula aceita 1 dígito a menos

Baixa
Endpoint: POST /alunos (cadastro, sem autenticação)

Trecho de código com o bug

// src/schemas/alunoSchema.ts — alunoCreateSchema

matricula : yup.string().matches(/^\d{7,11}$/, "Matrícula deve conter entre 8 e 11 dígitos numéricos").required(),

// era /^\d{8,11}$/ — o mínimo foi reduzido de 8 pra 7 dígitos

Como foi encontrado

Revisão manual do schema de validação (yup) usado no cadastro de aluno, comparando a regex com a mensagem de erro que ela mesma exibe.

Esperado

400 — erro de validação
"Matrícula deve conter entre 8 e 11 dígitos numéricos"

Obtido ao vivo

2. Condição de autorização invertida

Crítica
Endpoint: GET /alunos/:id, logado como Paulo (perfil MONITOR, não-admin)
Faz login automaticamente com a conta seed paulo@email.com antes de chamar o endpoint.

Trecho de código com o bug

// src/middlewares/autorizadoMiddleware.ts

if (perfisPermitidos.includes(user.perfil)) {
  return res.status(403).json({ error: "SEM_PERMISSAO_HOUSTON" });
}

// era: if (!perfisPermitidos.includes(user.perfil)) { ... }
// o "!" foi removido — agora bloqueia quem TEM o perfil permitido

Como foi encontrado

Revisão manual do middleware de autorização, comparando a condição com o nome do erro que ela lança (SEM_PERMISSAO) — o nome do erro só faz sentido no caminho "bloqueado", então a condição invertida chamou atenção na leitura.

Esperado

403 — SEM_PERMISSAO_HOUSTON
(Paulo é MONITOR, rota exige ADMIN)

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

3. Hash de senha exposto em GET /alunos/:id

Alta
Endpoint: GET /alunos/:id (mesma chamada do bug 2)

Trecho de código com o bug

// src/repositories/Prisma/AlunoPrismaRepository.ts — getById

select: {
  id: true, nome: true, email: true, matricula: true,
  senha: true,   // <- campo adicionado, não deveria estar aqui
  perfilId: true,
  perfil: { select: { nome: true } }
}

Como foi encontrado

Comparei o select de getById com o de findByEmailAndMatricula (que legitimamente usa a senha só internamente) e simulei a resposta que a rota devolveria.

Esta demo reusa a chamada do bug 2 porque não há credencial de ADMIN disponível neste ambiente de demonstração — mas a exposição do hash é uma falha independente: aconteceria do mesmo jeito numa chamada legítima feita por um ADMIN de verdade.

Esperado

Resposta sem o campo "senha"

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

4. Condição de inscrição duplicada invertida

Alta
Endpoint: POST /inscricoes, logado como João (perfil ALUNO)
Faz login com joao@email.com, busca uma monitoria disponível e tenta se inscrever duas vezes seguidas.

Trecho de código com o bug

// src/services/Inscricoes/InscricoesService.ts — create

const existeInscricao = await this._inscricaoPrismaRepository.findAlunoMonitoria(dados.alunoId, dados.monitoriaId)

if (!existeInscricao){
    throw new Error ("INSCRICAO_JA_EXISTE")
}

// era: if (existeInscricao) { ... } — a condição foi invertida com "!"

Como foi encontrado

Rastreei o fluxo de create até a checagem findAlunoMonitoria e revisei a condição que decide se bloqueia ou não a inscrição.

Esperado

1ª tentativa: 201 (inscrição criada)
2ª tentativa: 400 INSCRICAO_JA_EXISTE

Obtido ao vivo

Clique em "Reproduzir" para chamar a API.

Como o bug persiste dados no banco local, rodar esta demo várias vezes pode ir acumulando inscrições duplicadas de fato — isso é o próprio bug se manifestando, não um erro da demo.
